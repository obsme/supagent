supagent 0.9.6.6 - the AI agent inside Apache Superset
======================================================

What is in this folder
  supagent-0.9.6.6-py3-none-any.whl   the package for Superset 6.1 (pure Python; nothing else to install)
  supagent-guide.html / .pdf        the guide (install, LLM middleware, learning, screens)
  catalog.example.yaml              an example catalog, to adapt
  SHA256SUMS                        checksums

Upgrading? From 0.9.6.5, 0.9.6.4, 0.9.6.3, 0.9.6.2, 0.9.6.1 or 0.9.6: pip install this wheel on every host and
restart (tables v17 as before: nothing to run): "From 0.9.6.5 to 0.9.6.6" and the sections after it below. From
0.9.4, 0.9.2, 0.9.1 or 0.9.0: pip install this wheel on every host, superset supagent init once (schema 15 to 17:
new nullable columns; "part of" becomes links of the System map; the roles AI Admin, AI Editor, AI Viewer), restart:
"From 0.9 to 0.9.6" below says what changes and how to go back. From 0.8.x: pip install this wheel on every host,
superset supagent init once (schema 14 to 17), restart ("From 0.8 to 0.9.0" and "From 0.9 to 0.9.6" below). From
0.7.0 or 0.7.1: "Upgrade from 0.7 to 0.8.0" below (with this wheel: schema 13 to 17). From 0.6.0: the same steps
(init then goes from schema 9 to 17). From 0.5.4: the steps of "Upgrade from 0.5.4 to 0.6.0" with this wheel (schema
7 to 17). Steps 1-8 are for a new install.

A new Superset 6.1.0 installed from PyPI (tested 2 Oct 2026, on an empty PostgreSQL database owned by an ordinary
role): three packages must be pinned, or Superset itself does not start (none is about supagent):
   $PY -m pip install "apache-superset==6.1.0" "flask-caching==2.3.1" "flask-limiter<4" cachetools
   - Flask-Caching 2.5: SupersetMetastoreCache.__init__() got an unexpected keyword argument ...
   - Flask-Limiter 4 no longer brings "rich", which Superset's command line imports (superset db upgrade fails)
   - "cachetools" is imported by Superset (db_engine_specs/aws_iam.py) and no longer comes with its dependencies
     (the login page shows an error)
   Then Superset's own steps (superset db upgrade, superset fab create-admin, superset init), then step 1 below.

1. Install in Superset's virtualenv (pip only)

   PY=$(head -1 "$(command -v superset)" | sed 's/^#!//')
   $PY -m pip install supagent-0.9.6.6-py3-none-any.whl
   Superset 6.1: nothing else is needed (offline too).

2. Register it: one line in superset_config.py (no logic)

   from supagent import init_app as FLASK_APP_MUTATOR

   (already a FLASK_APP_MUTATOR?  import supagent; FLASK_APP_MUTATOR = supagent.chain(yours))

3. Tables, permissions, roles

   superset supagent init                        (--viewer-data all: the role AI Viewer reads every database)
   superset supagent grant <user> [<user>...] --role viewer|editor|admin    (or the roles in Superset's user list)
   AI Admin: everything (Superset's Admin and supagent's settings). AI Editor: charts, dashboards, datasets explored,
   SQL Lab, the knowledge written; no settings, no deletion. AI Viewer: reads and chats, changes nothing; its data
   as Superset gives it (a role or a group per team, or --viewer-data all). The role "AI Agent" of earlier versions
   is kept as it was (--role agent). Teams: Superset's groups; a note or a memory can be for a group's members.

4. The LLM (or in Superset: Settings -> Chat settings)

   company middleware (token from the middleware, renewed before it expires):
   superset supagent settings \
     --set llm.base_url=https://<llm gateway>/openai \
     --set llm.model=<model name> \
     --set llm.auth=middleware \
     --set llm.middleware.token_url=https://<middleware>/<token path> \
     --set llm.middleware.consumer_key=<consumer key> \
     --set llm.middleware.consumer_secret=<consumer secret> \
     --set llm.middleware.cert_path=/path/client.pem \
     --set llm.middleware.key_path=/path/client.key \
     --set llm.ca_bundle=/path/company-ca.pem
   a fixed token instead:  --set llm.auth=token --set llm.token=<token>
   no authentication:      --set llm.auth=none
   check:                  superset supagent test-llm

   search by meaning (optional; without it the search uses words only):
   superset supagent settings --set embed.model=bge-m3
     (the same gateway and authentication as the LLM; another endpoint: --set embed.base_url=...;
      give the model name exactly as the gateway lists it, e.g. GET <llm.base_url>/models)
   The vectors are kept in Superset's database (no extension needed), or in the knowledge store (step 8),
   or in a Qdrant server:
     --set search.vector_store=qdrant --set qdrant.url=http://<qdrant>:6333 [--set qdrant.api_key=...]

5. Restart the web server, the Celery workers and Celery beat.

   No workers yet, and no Redis? Superset's own database can be Celery's queue. In
   superset_config.py, after the SQLALCHEMY_DATABASE_URI line (Superset's other defaults kept):

     from superset.config import CeleryConfig as SupersetCeleryConfig

     class CeleryConfig(SupersetCeleryConfig):
         broker_url = "sqla+" + SQLALCHEMY_DATABASE_URI
         result_backend = "db+" + SQLALCHEMY_DATABASE_URI

     CELERY_CONFIG = CeleryConfig

   Then, with the celery of Superset's virtualenv, the same SUPERSET_CONFIG_PATH and the same
   environment as the web server (as services, Restart=always), and restart the web server:

     celery --app=superset.tasks.celery_app:app worker --pool=prefork -O fair -c 4 --loglevel=INFO
     celery --app=superset.tasks.celery_app:app beat --pidfile= -s /path/to/celerybeat-schedule --loglevel=INFO

   Workers on any number of hosts, ONE beat for all of them, the same supagent version everywhere.
   agent.executor = auto (default): questions go to the workers while one is alive (their
   heartbeat), each answered once; with no worker, or none free within 15 s, the web server
   answers. Settings -> Chat settings shows "Celery workers answer (N)". Delivered queue
   messages are deleted after agent.queue_keep_days (90) days.

6. Learn now (then every day at learn.hour, 02:00 by default, through Celery beat)

   superset supagent import-catalog catalog.yaml       (optional, recommended)
   superset supagent learn

   What today's run would do, without reading any data (objects, requests, minutes):
   superset supagent learn --plan

   One run per day. It is gentle: at most learn.max_requests_per_minute (60) requests per
   minute per database, one at a time, statistics of each metric or index refreshed every
   learn.profile_every_days (7) days, the database left for the day after
   learn.stop_after_errors (5) overload errors. Limit what is learned if the clusters are shared:
   superset supagent settings --set "learn.indices=batch-jobs*" --set "learn.metrics=node_*,batch_*"
   The run also classifies the knowledge (categories, at most learn.classify_per_run = 400 items a day);
   the first time, all at once: superset supagent classify --minutes 30

7. Documents and sites for the agent (optional): Settings -> Data dictionary -> Knowledge -> Documents and
   sites. Intranet sites need their domain allowed first:
   superset supagent settings --set "docs.allowed_domains=wiki.company.com"

8. The knowledge store in PostgreSQL (optional): the search by words (BM25), near spellings and meaning, and
   the chats, in PostgreSQL. In Superset's database (or another PostgreSQL: --set search.store_uri=...),
   as a superuser:
     CREATE EXTENSION IF NOT EXISTS vector; CREATE EXTENSION IF NOT EXISTS pg_trgm;
     CREATE EXTENSION IF NOT EXISTS pg_textsearch;
   Each one is optional: the store uses the ones it finds (none: the search without it, as in 0.5).
   pg_textsearch 0.5.x: do NOT put it in shared_preload_libraries (see step 1 of the upgrade below);
   1.x needs it there.
   Superset's database user needs the CREATE privilege on that database (the store is a schema of its own,
   supagent_store). Then:
     superset supagent init          builds it (the first time it finds the extensions)
     superset supagent store status  extensions, versions, size, warnings

From 0.9.6.5 to 0.9.6.6
=======================

The wheel on every host, restart; nothing to run (tables v17). Nothing changes by itself. New, when you want it:
three roles only, Admin, Editor and Viewer (supagent's AI Admin, AI Editor, AI Viewer and the earlier AI Agent
merged into Superset's Admin, Alpha and Gamma, these two renamed Editor and Viewer):
  1. Back up Superset's database (pg_dump -Fc -f superset-before-roles.dump "<Superset's database>"), then on one host
       superset supagent roles
     says what would change (the roles renamed and removed, the users and groups moved) and what stops it:
     superset_config.py naming Alpha, Gamma or an AI role (AUTH_USER_REGISTRATION_ROLE, AUTH_ROLES_MAPPING,
     PUBLIC_ROLE_LIKE, GUEST_ROLE_NAME...: it stops until they name Editor, Viewer or Admin), row level security
     filters or dashboards given an AI role (give them Admin, Editor or Viewer first; --force: they lose it).
  2. Write in superset_config.py what it says (e.g. AUTH_USER_REGISTRATION_ROLE = "Viewer", AUTH_ROLES_MAPPING
     values "Gamma" -> "Viewer", "Alpha" -> "Editor"), restart, then
       superset supagent roles --apply
     Alpha becomes Editor and Gamma Viewer (the same roles: their users, row level security filters and
     dashboards keep them); AI Admin's users get Admin, AI Editor's Editor, AI Viewer's and AI Agent's Viewer; the
     AI roles are removed; a copy of every user's and group's roles is kept (supagent_meta "roles_backup").
  3. From then on superset init and superset supagent init keep the three: Editor = Alpha and SQL Lab without
     deleting, with the knowledge written (no settings); Viewer = Gamma without anything that changes something,
     with the chat and the dictionary read; Admin = everything. The data: as before (a role or a group per team;
     every database: superset supagent init --viewer-data all). superset supagent grant <user> --role
     viewer|editor|admin gives them; superset fab create-user and other tools: Editor and Viewer instead of Alpha
     and Gamma.
  Back: superset supagent roles --undo (Alpha, Gamma and the AI roles again, every user's and group's roles as they
  were), with superset_config.py as before. Back to 0.9.6.5 while the three roles are in use: --undo first.

From 0.9.6.4 to 0.9.6.5
=======================

The wheel on every host, restart; nothing to run (tables v17). The System map in levels, display only (the agent
reads what it read before):
  - A category drawn inside another: Data dictionary -> Knowledge -> Categories -> Edit on the category -> Inside
    (e.g. disk inside server, partition inside disk, cpu inside server), as many levels as you need. Its values are
    drawn in that category's column, inside the value they are part of (else run on); the line at the bottom of a
    box opens or closes what is inside it. A category of categories.qualified (its values named after their server)
    is inside that category unless you choose otherwise.
  - A value part of another value of its own category is drawn inside it (a sub-subject inside its subject).
  - Filter the map on a part: the box above the map, or "Filter the map on it" in the part's panel. It shows what
    the part is in, what is inside it (every level down) and the parts it is linked to.
  - A big category's parts in groups by what they hold: servers by the components that run on them (the links
    "runs on" the learning reads in the metrics' labels, or that people draw), or by what they belong to (their
    application); each viewer chooses in the category's (i).
Back to 0.9.6.4: its wheel (the setting categories.inside is then unused).

0.9.6.4's sentences, read again by 0.9.6.5 the same way: among sentences of the same score the first one shown can
differ from 0.9.6.3's (0.9.6.4 reads the texts in the order they were made; 0.9.6.3 in the order the database gave
them); the sentences found are the same.

From 0.9.6.3 to 0.9.6.4
=======================

The wheel on every host, restart; nothing to run (tables v17). The System map answers in under a second on a big
platform: the sentences that explain the parts with no description are read by a job in the background (a thread of
the Superset process that serves the map), once for every process: they are kept in Superset's database (rows
map_hints* of supagent_meta), read again when the documents change or when parts are new. The first time after the
upgrade the map shows no such sentence for a few seconds, then shows them at its next reading. What exists now (the
documents that have pieces in the search, the metric families) is read once per document and kept 30 s per process.
The agent's answers are 0.9.6's (its code is unchanged). Back to 0.9.6.3: its wheel (the rows map_hints* are then
unused; delete them or leave them).

From 0.9.6.2 to 0.9.6.3
=======================

The wheel on every host, restart; nothing to run (tables v17). Two more kinds of secret are masked in what the
documents give before anything is kept: a DSN without a URL scheme (user:password@tcp(host:port)/db, as Go's MySQL
driver writes it) and a key held by a name that says so (SIGNING_KEY, apiKey...) given a literal value. A document
read before keeps its old text until it is read again: Documents and sites -> Read again (or wait for its next
reading) for the repositories whose code may hold such secrets. Back to 0.9.6.2: its wheel.

From 0.9.6.1 to 0.9.6.2
=======================

The wheel on every host, restart; nothing to run (tables v17). A Bitbucket repository can be given by its clone
address (https://host/scm/KEY/repo.git, a personal one ~user, https://bitbucket.org/ws/repo.git, with or without a
user@ in it): it is read as the repository, its default branch; a big repository's folders are all listed (the
listing grows with the files asked). Corrections of 0.9.6.1's notes: the secrets written in a file are masked in
every file a repository gives (its documentation and text files too, not only with "all its code"); and the check
before its release, at a new commit, asked for the three files that had changed: two were read and the third,
deleted, was removed (not "three changed files read"). Back to 0.9.6.1: its wheel.

From 0.9.6 to 0.9.6.1
=====================

On every host  $PY -m pip install supagent-0.9.6.6-py3-none-any.whl, then restart the web servers, the Celery workers
and beat. Nothing to run: the tables stay v17 (superset supagent init is not needed; run anyway, it says "schema
version 17 -> 17"). superset_config.py does not change. The agent's answers are 0.9.6's (its code is unchanged).

What changes:
  - The Context: a page no longer stops in the middle of a sentence (descriptions were cut at 200 characters); a
    data source's page gives its main indices' documents and time range and the fields (or labels) of its first
    three main indices or metrics (context.fields_shown, 30); an AI-written page cut by the LLM's length limit is
    asked to go on; one page whose LLM call fails no longer stops the build (the others are written, the search is
    updated, the run says "partial" with the pages not written). The pages change at the next build (a change waits
    for validation in To review, context.review).
  - To review: a new Context page has Reject (shown to nobody and not searched; proposed again only when its sources
    change); a change kept as it is is no longer proposed again with the same sources.
  - Documents and sites: the site's certificate is checked as before, or with a CA file (the document's, or
    docs.ca_bundle for every document: the company's root CA, a PEM file on every Superset host), or not checked
    (Edit: "certificate not checked", or docs.verify_tls off). A site whose certificate is not trusted says so.
  - Bitbucket: "A repository: read" = all its code too reads the source code (every common language, build and
    deployment files, 5,000 files at most a document), never the files that hold keys (.env, *.pem, *.key...) nor
    the vendored and built ones; the secrets written in the code are masked before anything is kept. A repository is
    read again only as far as it changed since the commit read last time (the same commit: nothing is read).
  - The search: a document's pieces are named after their page, so that a changed page makes again its pieces only.
    At the first index after the upgrade, the pieces of the documents read from an address are made again once
    (their vectors too: a few minutes for thousands of pieces).

Back to 0.9.6: pip install the 0.9.6 wheel on every host and restart. Nothing in the tables changed; the documents'
pieces are made again once more with 0.9.6's names; a Context page rejected with 0.9.6.1 is shown again by 0.9.6.

From 0.9 to 0.9.6
=================

On every host  $PY -m pip install supagent-0.9.6.6-py3-none-any.whl, then once, on one host:
      superset supagent init          tables: schema version 15 -> 17; the roles AI Admin, AI Editor, AI Viewer
Then restart the web servers, the Celery workers and beat. Settings -> Chat settings shows "supagent 0.9.6.6 (tables
v17)". Give people their role (superset supagent grant <user> --role viewer|editor|admin): the role AI Agent of
earlier versions is kept as it was, nobody loses an access.

What changes in Superset's database (nothing deleted, superset_config.py unchanged):
  - new nullable columns: supagent_link.both_ways, .seen_at, .proposed_drop, .proposed_drop_at; supagent_note.group_id;
    supagent_memory.group_id; supagent_recipe.title, .description, .how, .tasks, .summary_by, .summary_at;
    supagent_context.proposed_content, .proposed_sources, .proposed_kind, .proposed_hash, .proposed_at,
    .proposed_drop, .compared, .reviewed_by, .reviewed_at, .edited_by.
  - "part of" becomes links of the System map, once, at the init: what a value was part of (and the parts the
    learning proposed or an admin declined) become links of kind part_of, approved, proposed or declined as they were.
    The column supagent_facet.parents is kept as it was and no longer read.

What starts by itself (each one can be switched off in Settings):
  - The search reads a misspelled word as the knowledge spells it (search.spelling); documents are cut at their
    sections: their pieces are cut again at the next indexing (hourly with Celery beat, or superset supagent index).
  - Links read from the data: the values a metric's series carry together are linked at once
    (categories.label_links); a link the data has not shown for categories.data_link_days days is proposed for
    removal, never removed alone.
  - A change of a Context page waits for a person's validation (context.review).
  - Investigations: a part made of other parts (a pool and its servers) is checked with them (agent.with_parts).
  - A hard limit of tool calls per question (agent.max_steps, 16; agent.max_steps_big, 32, for an investigation).

Off by default (Settings to turn it on): the question read before the work (agent.read_question), written again
as one precise request in the team's names (shown as "Understood as" and given to the agent) by an LLM call of its
own, at the same time as the routing call; with it, a general question (a script, a definition) is answered without
the platform's data (agent.general_answers). Measured before the release, the reading misled follow-ups ("that"
read as the last figure, "the same weekday a week earlier" read with the names of unrelated charts).

Back to 0.9.4: pip install the 0.9.4 wheel on every host and restart. The new columns stay, unused. 0.9.4 reads
supagent_facet.parents as it was before the upgrade (what was made part of something in 0.9.6 is not in it); its
System map draws the links of 0.9.6 as interactions named by their kind ("part_of", "link:..."), their description
as their note; it shows no note nor memory kept for a group. The roles AI Admin, AI Editor and AI Viewer stay
(remove them in Superset's role list if they are not wanted).

From 0.8 to 0.9.0
=================

On every host  $PY -m pip install supagent-0.9.6.6-py3-none-any.whl, then once, on one host:
      superset supagent init          tables: schema version 14 -> 15
(three new nullable columns on supagent_link: detail, evidence, explained_by: the long explanation of an
interaction, where it was found, who explained it; the sentence an older proposed interaction kept as its note
moves to its evidence). Then restart the web servers, the Celery workers and beat. Settings -> Chat settings
shows "supagent 0.9.6.6 (tables v17)".

What starts by itself:
  - A question that asks what is wrong and why gets the system around it, two more tools (compare_groups,
    system_links), the investigation's steps and twice the calls of an answer (agent.max_steps). Nothing to set.
    compare_groups reads every measure of a table in one call (about a hundred small aggregations filtered on
    the question's scope, three at a time): with osagg 0.2.13 it takes 4 to 6 seconds, with 0.2.12 about twice
    that (same results). On a busy OpenSearch: Settings -> agent.compare_threads = 1 (one query at a time) and
    agent.compare_seconds (45: after it, no further field is read).
    When the rows wait on one value (a pool, a queue), the same call also compares every row that has this value
    (who else is there, what holds it): about sixty more aggregations, 8 to 10 seconds in all. To leave it to the
    agent's own calls: Settings -> agent.compare_follow = off.
    The days your team compares with: Settings -> agent.compare_against (yesterday, 1 week ago, 4 weeks ago by
    default; e.g. "yesterday, 1 week ago, 3 weeks ago, 3 months ago"; empty: the usual of the last days only).
    What makes it say more: in the catalog, a description of each time field of the tables of runs (released,
    started, ended), usual_of on the field that holds a usual value, and the relationships to the tables of
    changes and alerts (README, Investigations: What to prepare).
  - With the daily learning, the LLM reads the documents, guides, Context pages and team notes for the
    interactions they state between known parts (learn.interactions, on; at most ten minutes a day, each text
    once). What it finds waits in Data dictionary -> To review; nothing is drawn or used before an admin approves
    it. To leave it off: Settings -> learn.interactions.
  - An answer of an investigation marked Helpful keeps its path instead of its last query (To review). Every
    other answer marked Helpful keeps, with its query, its path (the tables and fields, the metrics and labels,
    the steps); one that ran no query to keep (a health check, a comparison) is learned as its path. An admin
    corrects a path in Edit before confirming.
  - The categories: the new values the learning reads in the data's fields (categories.fields) now wait in To
    review like the LLM's proposals (one click approves a category's found values); the values in use stay as
    they are. Parts that look retired are proposed there too (categories.retire_days, 14): nothing is retired by
    itself. To have the values of the data approved at once as before: Settings -> categories.review_all off.
  - superset supagent classify (and Classify now in the settings) is a run listed with the learning runs. Each
    Context build is followed by the classification (context.classify_after, on), which reads what the Context
    wrote; the nightly learning leaves the categories to it.
  - Every interaction of the System map gets a short and a long explanation (what to do when an investigation
    follows it), written by the LLM with the classification for the ones that have none (an admin's words are
    kept); the lines of the map carry no text, a click shows them. The agent gets them.
  - With the classification, the log tables are read for the interactions their lines state (learn.interactions_logs,
    on; no LLM): what they find waits in To review with its evidence, like the documents' proposals.
  - Log tables: compare_logs (what the logs say that they do not usually) is offered to investigations and to
    the questions about status; a table is read as logs when it has a text field (a message) and a time field.
    Its counting line by line stops after 40 seconds on a big table (said in its result).
  - A backup of the knowledge is written every day at 01:00 (the workers' beat) in supagent-backups in Superset's
    home, the last 14 kept (Settings -> Backups of the knowledge: backup.enabled, backup.hour, backup.keep,
    backup.dir). With several servers, set backup.dir to a directory they share. No secret is in a file.
What helps most, and what is missing: superset supagent check-system  (and --question "..." for one question).

Back to 0.8.2: pip install the 0.8.2 wheel on every host, then, in Superset's database, remove what 0.8 does not
know (it would draw a waiting interaction as an approved one, and give a path as a query to run; the path
kept with the other learned answers is ignored by 0.8; the three new columns of supagent_link stay, unused):
      DELETE FROM supagent_link WHERE status = 'proposed' AND a_ref LIKE 'facet:%' AND b_ref LIKE 'facet:%';
      DELETE FROM supagent_recipe WHERE tool IN ('investigation', 'path');
      DELETE FROM supagent_classified WHERE ref LIKE '%#links';
   and restart. The interactions an admin approved stay (0.8 draws them); the rejected ones stay too, unseen.
   The values found in the data that still wait in To review are approved by 0.8's next learning (its rule); the
   map's groups and moved categories, the categories' descriptions and the retirement proposals are ignored by
   0.8 and found again by 0.9.

Upgrade from 0.7 to 0.8.0
========================

What changes:
  - The pages: the explanations behind an "i" (a click shows them); bigger tabs; Learned by the agent in Knowledge;
    To review's panels close with their button; every delete asks in a small card; the chat panel on Superset's
    pages floats (moved, resized) or stays docked.
  - The catalog's classification "note" is "guide": init renames the entries, their history and their search
    pieces (the knowledge store too). A YAML with "note" still imports as guide.
  - Learned answers corrected before they are confirmed (a changed query runs first); words put on a table by hand
    (Where the data of the questions was).
  - The Context read as documentation, exported as Word or PDF; the System map (Knowledge -> System map).
  - Documents and sites: a sign-in (token, user and password, or a header), kept encrypted with Superset's
    SECRET_KEY: keep the same SECRET_KEY on every host (as Superset itself needs). Confluence and Bitbucket read
    through their APIs. An intranet address needs its domain in docs.allowed_domains, as before.
  - The subjects of a chat: each question gets the messages of its subject only (agent.subjects, on). Off: the last
    exchanges, as before.
  - Superset's database: new nullable columns (supagent_message.topic, supagent_recipe.edited_by, .edited_at,
    .previous, supagent_association.source, .added_by, supagent_doc.reader, .auth, .secret, supagent_link.note),
    schema 14 (15 with this wheel: three more columns of supagent_link, see "From 0.8 to 0.9.0"); the guides
    renamed; no table added, nothing deleted. superset_config.py does not change.

Steps (Superset stopped for a few minutes):
 1. Stop the web servers, the Celery workers and beat, on every host.
 2. Back up: pg_dump -Fc -f superset-before-0.8.0.dump "<Superset's database>"; $PY -m pip freeze > pip-before-0.8.0.txt
 3. On every host: $PY -m pip install supagent-0.9.6.6-py3-none-any.whl     ($PY -m pip show supagent: 0.9.6.6)
 4. Once, on one host: superset supagent init
      tables: schema version 13 -> 15
      knowledge store: N pieces of the catalog's notes are guides now      (when the store is used and had some)
 5. Start everything. Checks: Settings -> Chat settings shows "supagent 0.9.6.6 (tables v17)"; Data dictionary ->
    Knowledge -> Catalog: the former notes are guides; a question in the chat answers.

===========================

What changes (each one can be switched off):
  - Notes: every user of the agent may write notes (the chat's Notes button, "/note ..." or "/mynote ..." in the
    question box), for the team or for themselves; the agent finds them, says whose and of which day, never as a

  - The charts and dashboards looked at every night, with the Context build: each chart's last full day against
    the same weekday of the 4 weeks before; what each chart shows in words (LLM, charts.max_llm_calls a night);
    the agent answers "anything unusual on the X dashboard?" (chart_anomalies). Off: charts.scan=false. Gentle on
    the databases: charts.max_requests_per_minute (12 per database); one that answers it is overloaded is left for
    the next night.
  - Data dictionary -> Learned by the agent -> Where the data of the questions was: one row per table, pages.
  - Reliability fixes (always on): a period the question puts on a named time ("parcels shipped on ...",
    "tickets opened ...") is counted on that time field; an index's time field is its dataset's main time
    column when the dataset in Superset has one (from the first learning run after the upgrade: the next night,
    or superset supagent learn); a team rule's condition is applied the way the rule writes it ("... (F = 'V')
    ... never count them (F <> 'V')" leaves V out) and only to the tables it names; a question about the future

  - Data dictionary: Search lists everything found (pages, each name a link); categories added by hand, moved
    between categories, part of several others (a component of two applications), categories of your own read

    To review: Change... besides Approve and Reject.
  - A change: nothing the LLM finds is used before an admin approves it (categories.review_all, on): its
    categories and relations wait in To review (Approve all shown). categories.review_all=false: as in 0.6.
  - Not on: agent.cross_check (a test: a second, independent computation of the classic agent's figures).
  - Superset's database: 2 new tables (supagent_note, supagent_chart_scan) and one new column
    (supagent_facet.parents, .suggested, .origins), schema 13; nothing else changes.

Steps: as steps 3 to 9 of "Upgrade from 0.5.4 to 0.6.0" below (stop, back up, pip install this wheel on every

Upgrade from 0.5.4 to 0.6.0
===========================

What changes (each one can be switched off):
  - The router (MOA): before each answer, one short LLM call (60 s at most) chooses the kind of work
    (functional, technical, incident, charts, observability, infrastructure). Off: agent.router=false
  - The knowledge store, when vector, pg_trgm or pg_textsearch is in Superset's database: init builds it,
    then the search runs in PostgreSQL. Off: search.store=off (the search of 0.5.4)
  - The chats go into the store; each user can search their own (a search box above the chats).
    Off: search.chats=false
  - The catalog, the team memory, the Context, the documents and sites are now edited in the Data dictionary
    (Settings -> Data dictionary), no longer in Settings -> Chat settings. A save answers at once.
  - Categories of the knowledge: classified by the LLM with the daily learning (400 items a day at most).
  - Not changed: the classic pipeline answers (agent.pipeline = classic); the reranker is off.
  - Superset's database: 6 new tables (supagent_route, supagent_facet, supagent_tag, supagent_link,
    supagent_classified, supagent_item_use) and the schema supagent_store; no existing table or column
    changes, nothing is deleted. superset_config.py does not change.

A. Before the day (nothing changes yet)

 1. PostgreSQL, connected to Superset's database with psql (SHOW shared_preload_libraries needs a superuser or
    a role with pg_read_all_settings; the two SELECTs work for any user, Superset's too):

      SHOW shared_preload_libraries;
      SELECT extname, extversion, extnamespace::regnamespace AS schema FROM pg_extension
       WHERE extname IN ('vector', 'pg_trgm', 'pg_textsearch');
      SELECT has_database_privilege('<Superset database user>', current_database(), 'CREATE');

    - pg_textsearch 0.5.x in shared_preload_libraries: take it out (or upgrade pg_textsearch to 1.x), then
      restart PostgreSQL, BEFORE the upgrade. With 0.5.x a ROLLBACK after an error can fail ("ResourceOwnerEnlarge
      called after release started") and leave the session stuck; preloaded, that is every session, Superset's
      own too, with 0.5.4 already. Not preloaded, it is loaded only by the store's sessions, which never run a
      transaction. 1.x has the fix (and must be preloaded).
    - The extensions must be in Superset's database itself (CREATE EXTENSION is per database), in any schema.
    - CREATE privilege "f": GRANT CREATE ON DATABASE <Superset database> TO <Superset database user>;
      or keep the store off (step 8). Without it init says "knowledge store: not built" and the search of
      0.5.4 answers.
 2. Check the wheel (sha256sum -c SHA256SUMS) and keep the 0.5.4 wheel for a rollback.

B. The upgrade (Superset stopped for a few minutes)

 3. Stop the web servers, the Celery workers and Celery beat, on every host.
    (A running 0.5.4 process must not load files of 0.6.0: install while everything is stopped.)
 4. Back up (PY: the Python of Superset's virtualenv, as in step 1 of a new install):
      PY=$(head -1 "$(command -v superset)" | sed 's/^#!//')

      PY=$(head -1 "$(command -v superset)" | sed 's/^#!//')

      $PY -m pip show supagent | head -2                     (Version: 0.6.0)
    No other package is installed or changed (pydantic is already there). supagent[graph] is not needed.
 6. Once, on one host:
      superset supagent init
    It prints, among other lines (the rehearsal of this upgrade on a copy of the lab's database):
      tables: schema version 7 -> 9
      knowledge store: built (2064 pieces, 14146 names, pg_textsearch 0.5.0, vectors 1024) in 10.8 s
    and the warnings to read (e.g. pg_textsearch 0.5.0 is a pre-release: see step 1). "knowledge store: not
    used" or "not built" + the reason: the search of 0.5.4 answers; check with superset supagent store status.
    init takes a few minutes: the store (the lab at scale: 10,000 pieces, 380,000 names in 107 s), then the
    vectors of the last 2,000 chats' questions, older ones hourly after (the rehearsal: 3 minutes in all, the

      superset supagent store rebuild           (while people work; the search of 0.5.4 answers meanwhile)
