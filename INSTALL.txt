supagent 0.10.6.1 - the AI agent inside Apache Superset
=======================================================

What is in this folder
  supagent-0.10.6.1-py3-none-any.whl  the package for Superset 6.1 (pure Python; nothing else to install)
  supagent-guide.html / .pdf        the guide (install, LLM middleware, learning, screens)
  catalog.example.yaml              an example catalog, to adapt
  SHA256SUMS                        checksums

Upgrading? From 0.10.6: pip install this wheel on every host, restart; nothing to run: "From 0.10.6 to 0.10.6.1"
below. From 0.10.0: pip install this wheel on every host, superset supagent init once (no table changes: v18),
restart: "From 0.10.0 to 0.10.6" below (0.10.4 and 0.10.5 were not released: "What 0.10.5 brings" and "What 0.10.4 brings" too). From 0.9.6.9,
0.9.6.8, ... 0.9.6.1 or 0.9.6: pip install this wheel on every host, superset supagent init once (tables v17 to v18:
two new tables, nothing else changes), restart: "From 0.9.6.x to 0.10.6" below, and the sections after it for what
each 0.9.6.x after yours brought (in this wheel too, nothing more to run). From 0.9.4, 0.9.2, 0.9.1 or 0.9.0: pip
install this wheel on every host, superset supagent init once (schema 15 to 18: new nullable columns; "part of"
becomes links of the System map; the roles AI Admin, AI Editor, AI Viewer; the two tables of 0.10), restart: "From
0.9 to 0.9.6" and "From 0.9.6.x to 0.10.6" below say what changes and how to go back. From 0.8.x: pip install this
wheel on every host, superset supagent init once (schema 14 to 18), restart ("From 0.8 to 0.9.0" and the sections
after it). From 0.7.0 or 0.7.1: "Upgrade from 0.7 to 0.8.0" below (with this wheel: schema 13 to 18). From 0.6.0:
the same steps (init then goes from schema 9 to 18). From 0.5.4: the steps of "Upgrade from 0.5.4 to 0.6.0" with
this wheel (schema 7 to 18). Steps 1-8 are for a new install.

A new Superset 6.1.0 installed from PyPI (tested 2 Oct 2026, on an empty PostgreSQL database owned by an ordinary
role): three packages must be pinned, or Superset itself does not start (none is about supagent):
   $PY -m pip install "apache-superset==6.1.0" "flask-caching==2.3.1" "flask-limiter<4" cachetools
   - Flask-Caching 2.5: SupersetMetastoreCache.__init__() got an unexpected keyword argument ...
   - Flask-Limiter 4 no longer brings "rich", which Superset's command line imports (superset db upgrade fails)
   - "cachetools" is imported by Superset (db_engine_specs/aws_iam.py) and no longer comes with its dependencies
     (the login page shows an error)
   Then Superset's own steps (superset db upgrade, superset fab create-admin, superset init), then step 1 below.

1. Install in Superset's virtualenv (pip only)

   PY=$(head -1 "$(command -v superset)" | sed 's/^#!//')
   $PY -m pip install supagent-0.10.6.1-py3-none-any.whl
   Superset 6.1: nothing else is needed (offline too).

2. Register it: one line in superset_config.py (no logic)

   from supagent import init_app as FLASK_APP_MUTATOR

   (already a FLASK_APP_MUTATOR?  import supagent; FLASK_APP_MUTATOR = supagent.chain(yours))

3. Tables, permissions, roles

   superset supagent init                        (--viewer-data all: the role AI Viewer reads every database)
   superset supagent grant <user> [<user>...] --role viewer|editor|admin    (or the roles in Superset's user list)
   AI Admin: everything (Superset's Admin and supagent's settings). AI Editor: charts, dashboards, datasets explored,
   SQL Lab, the knowledge written; no settings, no deletion. AI Viewer: reads and chats, changes nothing; its data
   as Superset gives it (a role or a group per team, or --viewer-data all). The role "AI Agent" of earlier versions
   is kept as it was (--role agent). Teams: Superset's groups; a note or a memory can be for a group's members.

4. The LLM (or in Superset: Settings -> Chat settings)

   company middleware (token from the middleware, renewed before it expires):
   superset supagent settings \
     --set llm.base_url=https://<llm gateway>/openai \
     --set llm.model=<model name> \
     --set llm.auth=middleware \
     --set llm.middleware.token_url=https://<middleware>/<token path> \
     --set llm.middleware.consumer_key=<consumer key> \
     --set llm.middleware.consumer_secret=<consumer secret> \
     --set llm.middleware.cert_path=/path/client.pem \
     --set llm.middleware.key_path=/path/client.key \
     --set llm.ca_bundle=/path/company-ca.pem
   a fixed token instead:  --set llm.auth=token --set llm.token=<token>
   no authentication:      --set llm.auth=none
   check:                  superset supagent test-llm

   search by meaning (optional; without it the search uses words only):
   superset supagent settings --set embed.model=bge-m3
     (the same gateway and authentication as the LLM; another endpoint: --set embed.base_url=...;
      give the model name exactly as the gateway lists it, e.g. GET <llm.base_url>/models)
   The vectors are kept in Superset's database (no extension needed), or in the knowledge store (step 8),
   or in a Qdrant server:
     --set search.vector_store=qdrant --set qdrant.url=http://<qdrant>:6333 [--set qdrant.api_key=...]

5. Restart the web server, the Celery workers and Celery beat.

   No workers yet, and no Redis? Superset's own database can be Celery's queue. In
   superset_config.py, after the SQLALCHEMY_DATABASE_URI line (Superset's other defaults kept):

     from superset.config import CeleryConfig as SupersetCeleryConfig

     class CeleryConfig(SupersetCeleryConfig):
         broker_url = "sqla+" + SQLALCHEMY_DATABASE_URI
         result_backend = "db+" + SQLALCHEMY_DATABASE_URI

     CELERY_CONFIG = CeleryConfig

   Then, with the celery of Superset's virtualenv, the same SUPERSET_CONFIG_PATH and the same
   environment as the web server (as services, Restart=always), and restart the web server:

     celery --app=superset.tasks.celery_app:app worker --pool=prefork -O fair -c 4 --loglevel=INFO
     celery --app=superset.tasks.celery_app:app beat --pidfile= -s /path/to/celerybeat-schedule --loglevel=INFO

   Workers on any number of hosts, ONE beat for all of them, the same supagent version everywhere.
   agent.executor = auto (default): questions go to the workers while one is alive (their
   heartbeat), each answered once; with no worker, or none free within 15 s, the web server
   answers. Settings -> Chat settings shows "Celery workers answer (N)". Delivered queue
   messages are deleted after agent.queue_keep_days (90) days.

6. Learn now (then every day at learn.hour, 02:00 by default, through Celery beat)

   superset supagent import-catalog catalog.yaml       (optional, recommended)
   superset supagent learn

   What today's run would do, without reading any data (objects, requests, minutes):
   superset supagent learn --plan

   One run per day. It is gentle: at most learn.max_requests_per_minute (60) requests per
   minute per database, one at a time, statistics of each metric or index refreshed every
   learn.profile_every_days (7) days, the database left for the day after
   learn.stop_after_errors (5) overload errors. Limit what is learned if the clusters are shared:
   superset supagent settings --set "learn.indices=batch-jobs*" --set "learn.metrics=node_*,batch_*"
   The run also classifies the knowledge (categories, at most learn.classify_per_run = 400 items a day);
   the first time, all at once: superset supagent classify --minutes 30

7. Documents and sites for the agent (optional): Settings -> Data dictionary -> Knowledge -> Documents and
   sites. Intranet sites need their domain allowed first:
   superset supagent settings --set "docs.allowed_domains=wiki.company.com"

8. The knowledge store in PostgreSQL (optional): the search by words (BM25), near spellings and meaning, and
   the chats, in PostgreSQL. In Superset's database (or another PostgreSQL: --set search.store_uri=...),
   as a superuser:
     CREATE EXTENSION IF NOT EXISTS vector; CREATE EXTENSION IF NOT EXISTS pg_trgm;
     CREATE EXTENSION IF NOT EXISTS pg_textsearch;
   Each one is optional: the store uses the ones it finds (none: the search without it, as in 0.5).
   pg_textsearch 0.5.x: do NOT put it in shared_preload_libraries (see step 1 of the upgrade below);
   1.x needs it there.
   Superset's database user needs the CREATE privilege on that database (the store is a schema of its own,
   supagent_store). Then:
     superset supagent init          builds it (the first time it finds the extensions)
     superset supagent store status  extensions, versions, size, warnings

From 0.10.6 to 0.10.6.1
=======================

On every host  $PY -m pip install supagent-0.10.6.1-py3-none-any.whl, then restart the web servers, the Celery workers
and beat. Nothing to run: no table changes (v18), superset_config.py does not change. New setting: docs.skip_titles
(the titles of the wiki's and the sites' pages not read: "deprecated" by default). Back: the 0.10.6 wheel.
  - Documents and sites: a page under the document's page or named by its links that cannot be read (404, 403, a
    login page, not text) is skipped and counted; the others are read. Pages titled "deprecated" are not read, nor
    the pages they lead to. A page with no text is not kept; the pages under it and its links are followed.
  - Categories: every value can be removed (the ones seeded at the start too), alone or all the values the filtered
    list shows; the two aspects stay.

From 0.10.0 to 0.10.6
=====================

0.10.4 and 0.10.5 were measured and not released: what they bring comes with 0.10.6 (What 0.10.5 brings and What
0.10.4 brings, below).

On every host  $PY -m pip install supagent-0.10.6.1-py3-none-any.whl, then once, on one host:
      superset supagent init          tables: schema version 18 -> 18 (no table changes)
Then restart the web servers, the Celery workers and beat. superset_config.py does not change.

What changes:
  - The learning proposes what the texts say: the AI's "part of" only with a sentence of the texts naming both and
    saying it (quoted); its interactions only with a quote naming both ends; a subject (a topic) is no end of a link;
    one name, one value (no twin proposed in another category); a repository's tests, fixtures and examples
    (tests/, test/, testing/, testdata/, fixtures/, molecule/, examples/, e2e/, spec/) give no server, group or link
    (they stay in the search); where a part runs ends with its clause; Promtail's configuration is a log
    shipper's (its jobs no "monitors" link).
  - To review corrects: a proposed link's kind, direction, short and full explanations are edited before it is
    approved; each warning has its own actions (merge or reject, keep one direction, disable a document).
  - The Categories page has "+ Link" beside "+ Category": two parts, the kind from a list (belongs to, runs on,
    connects to, relies on, reads from, sends data to, monitors, triggers, is related to) or in your own words, the
    words people used before offered too.
  - The knowledge the agent searches: system_links gives the map's paths (depth 2-3: what the parts lead to, what
    leads to them) and, for a server or a group, what its failure reaches ("if_it_fails": what runs on it, on its
    servers and its group, then what depends on those, and further; a part that runs elsewhere too says where); a
    category's name lists its values; a question about how the system is built gets the System map, the documents
    and the Context first; a metric's usage lines ("a counter: use rate or increase, never SUM", the catalog's
    formulas) are kept whole in the knowledge given with a question.
  - A reply to the check of an answer written without a tool that speaks of the check keeps the answer it was sent
    on (never one with figures).
  - The reading's rules are version 0.10.6: the first reading after the upgrade reads every unit again once (a
    proposal the new rules no longer make is withdrawn).
Back: the 0.10.0 wheel on every host and a restart (no table to put back).

What 0.10.5 brings (not released; it comes with 0.10.6)
-------------------------------------------------------

  - What people add by hand changes only on evidence, with approval: a link a person drew is proposed for removal
    when the code or a configuration states its other direction, or when a sentence naming both of its parts denies
    it or puts it in the past (quoted); never for lack of evidence. A "Keep" is remembered with its reason, for every
    proposed removal: the same reason is not proposed again for that link.
  - A part with no description (one added by hand too) can get one written by the AI at the classification run,
    from what is known of it only (the sentences that name it, its links, where the data has it), marked "written
    by the AI" until a person saves one: learn.describe_values, OFF by default (measured on a lab map: 2 of 154
    gave a part a role no line states, 1 reversed a link, 7 said nothing; to be fixed and measured again).
  - The reading: environment files are configurations; an address naming a server or a VIP is the service running
    there whose technology its line says; templated passwords, fully qualified hosts, "x_backend" upstreams, VIP
    holders, "via" sentences, the link's kind from the address's line (README, "The documents and the code, read").
    The reading's rules changed: the first reading after the upgrade reads every unit again once.
Back: the 0.10.0 wheel on every host and a restart (no table to put back).

What 0.10.4 brings (not released; it comes with 0.10.6)
=======================================================

What changes (Settings -> Chat settings; the agent's checks made after 0.10.0 are OFF, see 0.10.3 and 0.10.4):
  - 0.10.1: an approval is searched at once by every server process; each wiki page read once when a wiki is given as
    several documents; To review filtered by a word, with Approve all shown / Reject all shown on what it shows; a
    classification run keeps time for the links; three Ansible idioms read (Jinja hosts, roles kept to a group,
    sample files).
  - 0.10.2: a value of the data named by a question is found whatever its writing, with the labels and fields that
    hold it (search.values); a part's links panel says where it is in the data; To review proposes where each
    category is in the data and lists what would confuse the agent or the search, with a fix (superset supagent lint).
  - 0.10.3: a reply that disputes or corrects an answer can be checked again on another path (agent.correction_check,
    off: measured with more silent mistakes on a held set).
  - 0.10.4, the learning and the search: the documents and the code read better (README, "The documents and the
    code, read"): denials and the past, subjects, arrows, tables of hosts, other languages, misspelled parts;
    Prometheus, Grafana, the Beats, Monit and Caddy configurations; Compose folders, aliases and extensions;
    versioned Kubernetes workloads and templated manifests; Ansible roles' services, databases and web sites; VIPs on
    the System map (a VIP an address with its services and the servers behind it); a question's part names found
    with other separators or a one-letter slip. The reading's rules changed: the first run after the upgrade reads
    every unit again once (no LLM call again: the LLM's reading of a unit whose text did not change is kept); a
    wiki or web page with lists has a new text once, at its next reading (its list items kept as items): new search
    pieces, and with knowledge.understand_llm on, one more LLM reading of that page.
    Reading takes about a quarter longer than 0.10.0's.
  - 0.10.4, what people made: a value, a link, a part_of or an item a person added is never removed nor proposed
    for removal because the documents, the LLM or the data say nothing of it (only a text saying a value was retired
    proposes its retirement, with the sentence; removals are proposed only for what the learning itself made, when
    its own source no longer states it, and wait for approval). reset-knowledge --categories now keeps the learned
    values a person's work rests on (a link a person drew to one or described, a value a person put inside one, an
    item a person gave one): only their learned links and items go; before, a link a person drew went with its
    learned end.
  - 0.10.4, the agent: off, to turn on by hand after measuring on your data: agent.claimed_query_check (an answer
    that says a query ran when none did), agent.bare_doubt_check (a doubt with nothing new), agent.announce_ing (a
    step announced in -ing), agent.link_limit_hint (a link's limit read on the peaks), tools.brief_crossings
    (check_health's brief crossings).
Back: the 0.10.0 wheel on every host and a restart (no table to put back).

From 0.9.6.x to 0.10.6
======================

First a backup of Superset's database (the way back to the data as it was):
      pg_dump -Fc -f superset-before-0.10.6.dump "<Superset's database>"
On every host  $PY -m pip install supagent-0.10.6.1-py3-none-any.whl, then once, on one host:
      superset supagent init          tables: schema version 17 -> 18
(two new tables: supagent_kunit, the units of the documents and the code that were read: a page, a file; and
supagent_kfact, what each states, with its line; nothing else changes, nothing deleted). Then restart the web
servers, the Celery workers and beat. Settings -> Chat settings shows "supagent 0.10.6.1 (tables v18)".
superset_config.py does not change.

What starts by itself:
  - The documents, the wiki pages and the repositories' files are read for what they state, without an LLM
    (knowledge.understand, on): who calls whom, the databases written and read, the caches, where the logs go, the
    metrics, what runs on which servers and the VIPs in front of them (an Ansible project's inventories, plays and
    variables, a Kubernetes repository, a Docker Compose file, keepalived, Prometheus, Grafana; README, "The documents
    and the code, read"). Each unit once at the next indexing (hourly, or superset supagent index), then only when its
    text changes. A wiki is now read to the last page its links lead to; a wiki given as several documents (one per
    space) whose pages link to each other has each page read once, by the first document that reaches it (0.10.1).
  - What they state is proposed for the categories and the System map, with where it was read (knowledge.propose,
    on): Data dictionary -> To review. Nothing is approved by itself, and nothing a person made or refused is
    changed. A large Ansible project can bring many proposals at once: review them part by part.
  - The Context: a page per part the documents describe, per server group, per repository (what it is: "An Ansible
    project: 2 inventories (12 hosts in 5 groups), 4 playbooks, 9 roles; what it deploys: ...") and per wiki space,
    at the next build of the Context.
  - The search: the System map's approved values and links are searched with the rest (their descriptions and the
    links' short and long explanations); a weak search is written again once by the LLM (search.rewrite = weak).
  - The agent: 0.9.7's checks of its work (Settings -> Chat settings, each one a setting, on); a question of how
    parts are connected gets the System map around them.
  - The data and the categories (0.10.2): a question naming a value of the data (a server, a service, a status),
    however written ("web shop", "WEB_SHOP" for "Web-Shop"), or a category value by one of its other names, gets
    which metrics' labels and indices' fields hold it, as the data writes it (search.values, on; only the databases
    the user may query). A part's links panel (Categories page, System map) says where it is in the data. To review
    proposes reading a category from a label or a field that holds several of its values ("Where the categories
    are in the data": an admin reads it, categories.fields, or sets it aside), and lists what could confuse the
    agent or the search, each with why and what to do ("What could confuse the agent or the search": a value
    proposed again in another category, one thing written two ways, the map in a circle, documents holding the same
    pages, a term defined twice; merge in one click where it applies, or Set aside). superset supagent lint prints
    the same list.

To read and propose at once rather than at the next indexing (before classifying the platform, for instance):
      superset supagent understand --propose      (--show also prints every link read, with its source)
      superset supagent index                     (the search's pieces and vectors)
Then To review: approve the parts and the links that are right (each shows the lines that state it). The
descriptions of what was approved, short and long, are written by the classification and the interactions'
reading (LLM), at the daily learning or at once:
      superset supagent classify --minutes 30
      superset supagent interactions --minutes 30
      superset supagent interactions --explain --minutes 30   (the explanations still missing, at once)
The links the AI explained before 0.10.0 were all explained as flows: a part that runs on a server "waited for" it.
Write again the AI's own explanations of those kinds (an admin's words stay; the flows keep theirs), again until it
says "done": true:
      superset supagent interactions --explain --again --kinds runs_on,monitors --minutes 30
(without --kinds: every explanation the AI wrote alone is written again)
An approval (To review, or on the System map) is searchable at the next question in every server process (0.10.1).
To review: the filter (a repository, a document, a part, a word) and "Approve all shown" / "Reject all shown"
review what one repository or one document proposed at once.

Settings that are new (superset supagent settings --set key=value, or Settings -> Chat settings):
  knowledge.understand          on    read what the documents and the code state (no LLM)
  knowledge.propose             on    propose it in To review (off: read for the search and the Context only)
  knowledge.understand_catalog  on    the catalog's guides, notes, rules, definitions and glossaries read too
  knowledge.understand_llm      off   the LLM reads the pages too (measured: it added more wrong links than right)
  search.rewrite                weak  a weak search written again once by the LLM (off: never)
  search.terms_uncapped         on    each term of a glossary a piece of its own in the search
  search.values                 on    a value of the data named by a question: where it is (labels, fields) first
  agent.value_elsewhere, agent.share_join_check, agent.period_window_check, agent.outer_join_check,
  agent.shown_sql_check         on    the checks of the agent's work (0.9.7)

Back to 0.9.6.9: pip install its wheel on every host and restart; nothing to run. The two new tables stay, unused
(0.9.6.9 does not read them; its superset supagent init, if run, writes the schema number 17 again and leaves them).
The values and links proposed from the documents stay in To review as proposals, like the learning's own. The System
map's pieces stay in the search until 0.9.6.9's next indexing removes them (hourly; superset supagent index at once).
The data exactly as it was before the upgrade: the backup (pg_restore; what was learned or approved since is lost).
Rehearsed on a copy of a lab's database (0.9.6 -> 0.10.2 -> 0.9.6.9, with and without its init -> 0.10.2 again):
the settings kept, nothing doubled, the pages, the System map and To review at each step, a chat question answered
on 0.10.2, the backup restored identical. 0.10.4 changes no table: on a copy of a lab's data upgraded from 0.10.0 to 0.10.4,
the tables stayed v18 and the 28 settings identical.

From 0.9.6.6 to 0.9.6.7
=======================

The wheel on every host, restart; nothing to run (tables v17). Nothing changes by itself. New: a way to wipe what
the learning made and make it again (the Context, the categories' values and their descriptions, the System map's
links and theirs), e.g. once a version reads the documents better:
  1. superset supagent reset-knowledge --context --categories --links
     says what would go and what stays; nothing is changed. Goes: the Context pages the agent wrote, the values read
     in the data or proposed by the LLM with the items they were given, the links neither drawn nor described by a
     person. Stays: the values a person added (with their descriptions), the links a person drew or described, the
     Context pages a person wrote, the items a person gave a value; with --all those go too, and the categories'
     descriptions. The categories themselves (their names, fields, what is inside what) always stay.
  2. The same with --yes: a backup of the knowledge first (in backup.dir; when it cannot be made, e.g. while a
     learning runs, nothing is wiped), then the wipe.
  3. Make them again, in this order (each can take a while on a big platform):
       superset supagent learn                      the values read in the data's fields and labels, their links
       superset supagent classify                   the items given their categories, the relations texts state
       superset supagent interactions --again       the links the documents, guides, Context pages and notes state
       superset supagent context --build --force    the Context written again
     then Data dictionary -> To review: approve the values and the links proposed (categories.review_all on).
  Back as before: superset supagent restore <the backup's name> --parts categories,context --yes (superset supagent
  backups lists them).

From 0.9.6.5 to 0.9.6.6
=======================

The wheel on every host, restart; nothing to run (tables v17). Nothing changes by itself. New, when you want it:
three roles only, Admin, Editor and Viewer (supagent's AI Admin, AI Editor, AI Viewer and the earlier AI Agent
merged into Superset's Admin, Alpha and Gamma, these two renamed Editor and Viewer):
  1. Back up Superset's database (pg_dump -Fc -f superset-before-roles.dump "<Superset's database>"), then on one host
       superset supagent roles
     says what would change (the roles renamed and removed, the users and groups moved) and what stops it:
     superset_config.py naming Alpha, Gamma or an AI role (AUTH_USER_REGISTRATION_ROLE, AUTH_ROLES_MAPPING,
     PUBLIC_ROLE_LIKE, GUEST_ROLE_NAME...: it stops until they name Editor, Viewer or Admin), row level security
     filters or dashboards given an AI role (give them Admin, Editor or Viewer first; --force: they lose it).
  2. Write in superset_config.py what it says (e.g. AUTH_USER_REGISTRATION_ROLE = "Viewer", AUTH_ROLES_MAPPING

Learn again from scratch (every database, or --database NAME):
   superset supagent forget-learned          (shows what would be forgotten; nothing changes)
   superset supagent forget-learned --yes    (forgets it; catalog, learned answers, chats and
                                              admins' dictionary edits are kept)
   superset supagent learn --minutes 240     (or wait for the daily run)

Many users: without Celery workers (step 5), answers run in the web server; start it with several
workers and threads, e.g. gunicorn -w 4 -k gthread --threads 8 ... "superset.app:create_app()".
The number of answers in parallel is mostly set by the LLM server (how many requests it serves
at once).
Remove: delete the config line and restart (the supagent_* tables stay until you drop them).
